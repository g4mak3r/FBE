# FBE Flow · Foundation

## Принципы

Один локальный Python-процесс: FastAPI + SQLite + Jinja2 + vanilla JavaScript.
Данные аккаунтов определяют товары, категории, идентификаторы, склады, внешние статусы
и доступные действия. В core нет условий по конкретным продавцам или внешним системам.
Нет ORM, брокеров, Redis/Celery, микросервисов и frontend frameworks.

## Границы и зависимости

| Часть | Ответственность |
| --- | --- |
| `core/` | SQLite, миграции, нормализованные DTO, ошибки, контракт адаптера и registry |
| `modules/sellers.py` | Реестр локальных продавцов |
| `modules/connections.py` | Подключения аккаунтов и обнаруженные возможности |
| `modules/records.py` | Четыре отдельные модели/таблицы: products, warehouses, supplies, orders |
| `modules/operations.py` | Персистентная очередь, жизненный цикл и один thread worker |
| `modules/settings.py` | JSON-настройки конкретного seller |
| `integrations/` | Отдельные адаптеры: авторизация, внешние HTTP API, преобразование данных |
| `web/` | Проверка HTTP-ввода, seller в URL, Jinja shell и JS |
| `app.py` | Сборка компонентов и управление lifespan |

Направление: `web → modules → core`, `integrations → core`.
Только `app.py` связывает реализацию adapters с modules через registry.
Core не импортирует web, modules или реализации integrations; modules не импортируют
внешние SDK/API. Простые межмодульные проверки seller/connection допустимы.
Четыре таблицы пока обслуживаются одним небольшим store. Доменное поведение
выделяется в отдельный модуль при появлении реального контура, без generic repository framework.

## Seller isolation

- Seller обязателен в URL и аргументах всех обращений к операционным данным.
  Текущий seller хранится в URL страницы, а не в глобальной переменной сервера.
- Поиск записи всегда включает `seller_id` и ID. Чужой ID возвращает `404`.
- Каждая операционная таблица содержит `seller_id`. Настройки имеют PK `(seller_id, key)`.
  Внешняя идентичность: `(seller_id, connection_id, external_id)`.
- Все связи операционных данных используют составные внешние ключи, включающие seller.
  Связи заказа/поставки также включают connection: нельзя сослаться на склад другого аккаунта.
  `PRAGMA foreign_keys=ON` устанавливается на каждом соединении.
- Только реестр продавцов и внутренний диспетчер/recovery имеют общий обзор.
  Диспетчер передает seller из выбранного задания в каждое последующее действие.
- Это изоляция данных рабочих пространств одного локального пользователя, а не
  многопользовательская авторизация. CLI слушает только `127.0.0.1`; HTTP проверяет
  Host, JSON, заголовок `X-FBE-Flow: 1` и Origin при изменениях. Для сетевого режима
  сначала потребуется отдельный контур авторизации и проверки доступа к seller.

## Integrations

Адаптер реализует `IntegrationAdapter` и регистрируется в `installed_adapters()`.
`describe(config)` проверяет параметры и возвращает реальный ID аккаунта и его
`OperationSpec`. Возможности сохраняются как снимок на момент подключения;
адаптер обязан проверять актуальную доступность и входные параметры при `execute`.
`execute(ConnectionContext, key, payload)` возвращает единый `OperationResult`:
необязательный `batch: NormalizedBatch` и `data` с JSON-данными результата без секретов.
Sync возвращает batch, команда может вернуть только data; допустимы оба поля или пустой
результат. Отдельных иерархий read/command, командной шины и автоматического retry нет.
Контекст содержит seller, connection, внешний account ID и параметры. Адаптер не получает БД.

Нормализация явная: свои поля DTO, произвольные данные в `attributes`, категория
и именованные идентификаторы приходят от источника. Внешние статусы остаются строками;
семантическое сопоставление появится только при необходимости конкретного контура.
Пакет сохраняется одной транзакцией, upsert сохраняет внутренний ID.
Ссылки должны указывать на уже сохраненную запись или запись того же пакета.
Удаление отсутствующих записей, полный reconcile и сложные связи пока не реализованы.

### Product identity

`products` сейчас содержит записи конкретного источника, а их внутренний UUID — ID
этой записи, не утверждение об идентичности физического trade item во всех системах.
Идентификаторы, включая GTIN при наличии, сохраняются как данные источника; отсутствие,
множественность и совпадение identifiers не вызывают автоматического объединения.
Canonical product/identifier layer отложен до второго реального источника и проверяемых
правил сопоставления. Его можно добавить отдельными seller-scoped таблицами и связями
к существующим source records, сохранив их ID, metadata и происхождение данных.

Foundation поставляется без адаптеров, seed-аккаунтов и production demo-данных.
Тестовый адаптер существует только в `tests/`. `config`, settings и payload предназначены
для данных без секретов. Перед первым реальным подключением адаптер должен реализовать
безопасное хранение credentials отдельно от этих JSON-полей; например Windows Credential Manager.
Тексты внешних исключений не сохраняются и не возвращаются пользователю.

## Фоновые операции и SQLite

`queued → running → succeeded/failed`; после аварии `running → interrupted`.
Очередь сохраняется между запусками. Claim использует `BEGIN IMMEDIATE`.
Partial unique index запрещает повторное активное задание с одинаковыми
`(seller_id, connection_id, operation_key, scope_key)`. Необязательный явный scope
различает цели; без него действует прежняя дедупликация на уровне connection/action.
Контур должен выводить стабильный scope из проверенных данных цели. Core не угадывает
его по payload и не вводит собственные типы целей; это ключ дедупликации, не проверка
прав на внешний объект и не внешняя idempotency key. Разные scopes допускают несколько
ожидающих заданий; worker по-прежнему выполняет их последовательно. Общий scope и
scope цели не исключают друг друга: блокировки между разными действиями здесь не моделируются.
Нормализация при наличии batch, результат и `succeeded` фиксируются одной транзакцией.
Сохраненный `result` имеет `{counts, data}`: counts — счетчики нормализованных записей
или null при отсутствии batch, data — данные результата адаптера. Migration 002 добавляет
scope с прежним default и оборачивает сохраненные результаты v1, сохраняя счетчики.
Внешний вызов выполняется вне транзакции, с ограниченными таймаутами в адаптере.
SQLite работает в WAL; соединение открывается и закрывается для каждого действия.

OS file lock допускает один процесс на data directory. Lifespan запускает worker
и завершает текущую операцию перед освобождением lock. При сбое worker `/health`
возвращает `503`. Прерванные/ошибочные задания автоматически не повторяются:
внешний side effect мог произойти до фиксации в SQLite. Exactly-once для внешних API
не обещается; следующий контур должен определить idempotency/reconciliation.

## Добавление следующих контуров

1. Добавлять только нужные сценарию поля, поведение и HTTP routes.
2. Каждую новую таблицу и связь делать seller-scoped; ID от клиента не заменяет scope.
3. Внешнюю специфику держать в отдельном адаптере; capabilities получать от аккаунта.
4. Миграции добавлять новым нумерованным SQL-файлом, существующие не переписывать.
   Миграции транзакционные; более новая схема БД отклоняется. Перед обновлением сохранять БД.
5. Проверять isolation через два sellers, составные FK, rollback и перезапуск заданий.
6. Расширять UI вместе с реальным контуром. Foundation ограничен shell, подключениями,
   настройками и состоянием операций. Wildberries, маркировка, печать, экономика
   и полноценный каталог в этот этап не входят.
