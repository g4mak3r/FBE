# Ozon и интернет-магазин на Яндекс KIT: этапы 5–6

Flow 0.6.0 объединяет WB и Ozon в разделе «Маркетплейсы» с переключателем.
Выбор сохраняется для продавца. Старые ссылки `/wb` и `/ozon` работают.
Магазин — отдельный раздел `/store`; название меняется в «Название блока магазина»
и сохраняется в `store.name` этого продавца. Название не меняет внешнюю идентичность KIT.

## Источники и границы проверки

Спецификации исследованы 02.10.2026. Для KIT использованы первичные источники:

- [Введение и собственный API KIT](https://yandex.ru/dev/kit/ru/).
- [Авторизация](https://yandex.ru/dev/kit/ru/authorization).
- [Лимиты запросов](https://yandex.ru/dev/kit/ru/rate-limits).
- [Официальная спецификация Яндекса](https://github.com/yandex/kit-skills/blob/main/skills/yandex-kit-cabinet/references/openapi.json).
- [Правила работы с заказами](https://github.com/yandex/kit-skills/blob/main/skills/yandex-kit-cabinet/references/orders.md).
- [Коды маркировки и кассовые проверки](https://yandex.ru/support/kit/ru/orders/datamatrix).

KIT использует `https://api.kit.yandex.net`, Bearer-токен одного магазина и UTC.
Интервал 350 мс соответствует более строгому опубликованному лимиту 3 запроса/сек;
вспомогательный README Яндекса указывает 10/сек, поэтому выбран строгий предел.
API Яндекс Маркета не используется вместо KIT.

Для Ozon: [Seller API](https://docs.ozon.ru/api/seller/) и
[официальные сообщения об изменениях](https://t.me/s/OzonSellerAPI).
Сайт спецификации не удалось прочитать напрямую из среды разработки: защита сайта
давала цикл перенаправлений. Исследована копия OpenAPI, выпущенная Ozon, из
[зеркала](https://github.com/Slimpers/Ozon-API-parser-MD/blob/main/md/seller/openapi.json),
blob `f825ec7e8670b59e45344326b9eec8e54aab2907` (API 2.1), и сопоставлены актуальные
версии методов с официальными сообщениями. Зеркало не заменяет живую приемку и не
доказывает отсутствие последующих изменений. Незнакомый ответ не считается успехом.

## Подключения

Ключи хранятся через Windows DPAPI CurrentUser, вне SQLite/HTML/журналов.
В config только seller-bound ссылка, account ID, ИНН и локальный режим чтения.
Ozon проверяет Client-Id, Api-Key, роли и `company.inn`. KIT проверяет `/store` и
`/users/current`; `/store` не возвращает ИНН. ИНН KIT заявляется оператором для
привязки к его производственному ЧЗ и явно не помечается подтвержденным KIT.

Замена ключа разрешена после окончания очереди этого подключения: новый ключ должен
сохранить аккаунт и ИНН, config меняется атомарно, прежний секрет удаляется после успеха.
Режим чтения в FBE дополнительно запрещает команды; права API проверяет сама платформа.
Интервал Ozon 600 мс, KIT 350 мс; 429 увеличивает паузу. Автоматического retry нет.

## Ozon FBS

| Возможность | Метод и проверка |
| --- | --- |
| Товары | `/v3/product/list` и `/v3/product/info/list`: card ID и posting SKU раздельны |
| Склады | `/v2/warehouse/list`, курсор; устаревший v1 не используется |
| Отправления | `/v3/posting/fbs/list`, окно 30 дней; свежий состав `/v3/posting/fbs/get` |
| Отгрузки | `/v2/carriage/delivery/list`: только существующие ID, чтение на сегодня |
| Возвраты | `/v1/returns/list`, FBS и курсор; чтение без автоматического возврата денег/КМ |
| Экземпляры | `/v6/fbs/posting/product/exemplar/create-or-get` |
| Назначение КМ | `/v6/fbs/posting/product/exemplar/set`, полный набор экземпляров отправления |
| Проверка КМ | `/v5/fbs/posting/product/exemplar/status`, точный КМ каждого экземпляра и `passed` |
| Сборка | `/v4/posting/fbs/ship`, один пакет, свежая проверка состава/всех КМ |
| Отмена | `/v2/posting/fbs/cancel`, причина из `/v2/posting/fbs/cancel-reason/list` |

Товар связывается с собственной доступной карточкой НК, GTIN и разрешенной группой ЧЗ
с тем же ИНН. Каждый КМ проверяется True API непосредственно перед записью: ввод в
оборот, владелец, GTIN, группа, упаковка UNIT и дополнительные ограничения статуса.
Передается сохраненный полный DataMatrix с криптохвостом и точными символами GS.

Тело назначения сохраняет остальные SKU, экземпляры, ГТД/РНПТ и другие сведения,
которые принимает метод set. Изменение экземпляров после подготовки блокирует запись.
Чужие коды не перезаписываются. HTTP 200 означает только прием запроса; асинхронная
проверка каждого экземпляра определяет результат. `failed` без ошибок не доказывает,
что запись не состоялась. Проверенные позиции можно назначать последовательно;
готовность всего отправления требуется при сборке, а не при проверке отдельной позиции.

Сборка требует всех подтвержденных маркируемых позиций и повторной проверки ЧЗ.
`awaiting_deliver` подтверждает готовность к отгрузке, а не доставку покупателю.
Неизвестные дополнительные требования ГТД/IMEI и т.п. направляют оператора в кабинет.
FBO, автоматическое разделение пакетов, создание/закрытие carriage, печать и изменение
цен/остатков Ozon не реализованы в этом этапе.

## KIT: заказы, платежи и доставка

| Возможность | Реализованное поведение |
| --- | --- |
| Товары | `/v1/variants`: конкретные продаваемые варианты, а не только родительский product |
| Склады | `/v1/warehouses`, ACTIVE/ARCHIVED, все страницы |
| Заказы | `/v1/orders`, только page/per_page; локальный поиск и статус после чтения |
| Состав | `/v1/orders/{id}`: все delivery_chunks, позиции, количество, отказы, доставка/треки |
| Оплата | payment.status, суммы, acquiring fields и статусы чеков сохраняются из KIT |
| Подтверждение | `/v1/orders/{id}/confirm`, без тела, только WAIT_FOR_CONFIRMATION |
| Отмена | `/v1/orders/{id}/cancel`, без тела, отдельное явно подготовленное действие |
| Своя доставка | `/v1/orders/{id}/delivery/complete`, без тела, самовывоз или MERCHANT_SHIP |
| Цены | `/v1/variants/prices/bulk_update`, Decimal-строки и явный null для сброса |
| Остатки | `/v1/variants/stocks/bulk_update`, абсолютное quantity пары вариант/склад |

Каждый переход проверяется повторным чтением; confirm не идемпотентен и при потерянном
ответе не повторяется. Завершение доставки — отдельное решение оператора, доступное
из WAIT_FOR_DELIVERY. Яндекс Доставка, CDEK, Ozon Доставка и другие внешние службы
сами подтверждают доставку. Состояние `CANCELLATION_IN_PROGRESS` подтверждает принятую
отмену, но не возврат денег. PARTIAL_REFUND/FULL_REFUND не подменяются отменой.

Цены/остатки: до 100 элементов в действии, перед записью сравнение свежих значений с
подготовленным снимком, затем чтение каждого результата. Сохраняются matched/missing
при частичном результате. Цены: положительные строки до 15 целых цифр и двух дробных;
экспоненциальная запись запрещена. Зарезервированное KIT количество не изменяется.

### Маркировка магазина

В публичной спецификации KIT нет записи КМ в заказ, произвольного изменения состава,
частичного возврата, печати накладных или создания чеков. Flow готовит и резервирует
полные КМ для конкретной позиции, проверяет ЧЗ и оставляет `awaiting_manual`.
Оператор копирует полные КМ, вносит их через кабинет KIT и выполняет кассовую проверку.

Для quantity=1 чтение точного `truthful_label == full_code` подтверждает наличие КМ.
Это подтверждение поля заказа, а не самостоятельный вердикт разрешительного режима.
Формат нескольких КМ в одном строковом поле не документирован: Flow не выдумывает
список через запятую/JSON. Для quantity>1 ручной контур остается в KIT, включая
подтверждение и завершение заказа, требующее проверки всех маркируемых единиц.
Перед confirm/complete проверяются требования маркировки актуальных вариантов,
подтвержденные назначения, метаданные KIT и актуальные КИ True API. Частичный выкуп
маркируемых позиций направляется в кабинет.

Касса, эквайринг и интеграции доставки выбираются в KIT, без жесткой привязки к
CloudPayments/Robokassa/Ozon Seller. Flow читает их результат и не создает повторный
кассовый чек или автоматический документ вывода из оборота. Как именно выполняется
вывод при онлайн-оплате/получении, зависит от подключенных кассы и доставки;
проверка True API в Flow не заменяет разрешительный режим кассового ПО.

## Общий резерв, очередь и обновление

Migration 006 сохраняет migrations 001–005. Перед обновлением существующей базы
создается `flow.before-v6.sqlite3`. Старые резервы WB перенесены в общий уникальный
резерв физического кода. В WB/Ozon/KIT и между продавцами невозможно повторное
назначение одного сохраненного КИ. Отмена заказа после передачи не освобождает КМ.
Освободить можно черновик или доказанный отказ до приема, без внешнего удаления кода.
Если старая база содержит противоречащие назначения одного физического КМ, миграция
откатывается и сохраняет исходную базу/backup; противоречие не удаляется автоматически.

Перед записью коммитится точное тело/digest и submitting; ACK/receipt сохраняются
до последующей сверки и независимо от коммита worker. Таймаут, неверный JSON, 409,
5xx или остановка процесса во время записи дают unknown. Запись не повторяется.
Сверка читает внешнее состояние; accepted/pending проверяются в фоне каждые 30 секунд.
Generic очередь не исполняет подготовленное действие без его scope/state/digest.

Sync разбит на долговечные задания по страницам. Ошибка/повтор курсора/повтор страницы
оставляет partial coverage; последнее полное чтение показано отдельно. Исторические
локальные строки не удаляются автоматически. Успех обхода означает успешное чтение
страниц API, а не атомарный снимок меняющегося каталога/заказов.

## Проверки

Изолированные transport/signer проверяют полную цепочку НК/СУЗ/нанесение/ввод → Ozon
и ручную подготовку KIT, точные GS, owner/GTIN/group/status, каждый экземпляр, общий
резерв трех каналов, ACK/unknown/restart, pagination, частичные результаты, замену
ключей, seller isolation, цены/остатки и миграции. Браузерная приемка дополнительно
проверяет переключатель, название магазина, связи с НК, задания, оплату/доставку,
диалоги и мобильную ширину. Живые ключи и УКЭП не использовались: промышленная приемка
проводится на действующих кабинетах пользователя, с проверкой кассы и доставки KIT.
