# Честный Знак: этапы 2–3

Версия Flow 0.3.0 расширяет сохраненные подключения этапа 1 без потери карточек
или секретов. Это операции НК, СУЗ и оборота в указанном ниже наборе сценариев.
Не требуется другой процесс, брокер или отдельный frontend.

## НК: изменение и публикация

| Метод НК | Назначение |
| --- | --- |
| `GET /v3/attributes?cat_id=...&attr_type=a` или `isset_id=...` | Атрибутивный состав выбранной категории/набора |
| `GET /v3/feed-product?good_ids=...` | Свежие собственные карточки; чтение пакетами до 25 ID |
| `POST /v3/feed` | Передача правок/удалений атрибутов и флага moderation |
| `GET /v3/feed-status?feed_id=...` | Внешняя обработка переданного пакета |
| `POST /v3/feed-product-document` | Получение XML для подписания, goodIds и publicationAgreement |
| `POST /v3/feed-product-sign-pkcs` | Массив goodId и отделенных подписей XML в base64 |

Для массовых правок доступны только общие атрибуты выбранных карточек, кроме
запрещенных `attr_type=b`. Проверяются multiplicity, пресеты и attr_value_type;
удаление допускается для существующего значения. Карточки в модерации, архиве
и с неизвестным состоянием не изменяются. Отсутствующие детали не считаются пустой карточкой.

Подготовка сохраняет версии и таблицу «Было / Будет». Перед отправкой повторно
читаются все карточки: изменение любой версии останавливает отправку.
Для публикации XML запрашивается повторно и должен совпасть с просмотренным XML.
Подпись строится над его точными UTF-8 байтами; локальный XML не конструируется.
Результат подписания проверяется для каждой выбранной позиции. Часть успешных
подписей дает `partial`, а не возможность отправить весь пакет повторно.

Feed ID означает приём, затем проверяется feed-status. Ошибки по позициям сохраняются;
неизвестный статус остается в обработке. После терминального результата собственные
карточки обновляются с сохранением UUID, а ETag сбрасывается для следующей синхронизации.
Если чтение обновлений не удалось, бизнес-результат сохраняется, а задание содержит
`refresh_error=nk_refresh_failed`; пользователь может синхронизировать каталог.

## СУЗ: заказ, блоки и нанесение

Промышленный адрес — `https://suzgrid.crpt.ru`, тестовый —
`https://suz.sandbox.crptech.ru`. Каждый запрос содержит выбранный `omsId` и
заголовок `clientToken`. Токен получается по присоединенной УКЭП подписи challenge
через True API `POST /auth/simpleSignIn/{omsConnection}`; кеш ограничен 9 часами
и отделен от токена True API. На 401 кеш сбрасывается без повторения бизнес-запроса.
Выбор новых OMS-параметров блокируется при незавершенных заданиях/документах СУЗ.

| Метод СУЗ API 3.0 | Назначение |
| --- | --- |
| `GET /ping` | Проверка подключения и соответствия OMS |
| `POST /order` | Заказ products и attributes выбранной группы |
| `GET /order/list` | Заказы, группы, статусы и буферы |
| `GET /order/status?orderId=...&gtin=...` | Статус и остаток буфера |
| `GET /order/codes/blocks?orderId=...&gtin=...` | Уже выданные блоки |
| `GET /codes?orderId=...&gtin=...&quantity=...` | **Новая выдача КМ**, один вызов через журнал |
| `GET /order/codes/retry?blockId=...` | Повторное чтение ранее выданного блока |
| `POST /utilisation` | Отчёт UTILISATION с полными КМ в sntins |
| `GET /report/info?reportId=...` | Обработка отчёта |
| `POST /order/close` | Закрытие заказа/выбранного буфера |
| `GET /receipts/receipt?resultDocId=...` | Квитанция по её ID |
| `POST /receipts/receipt/search` | Поиск квитанции с filter.orderIds или filter.sourceDocIds |
| `GET /receipts/document?resultDocId=...&docId=...` | Исходное содержимое документа для сверки |

В таблице опущен общий префикс `/api/v3`. Заказ проверяет собственную карточку
GTIN и good_mark_flag. serialNumberType — OPERATOR или SELF_MADE; для SELF_MADE
число уникальных serialNumbers должно совпадать с quantity. templateId и cisType
не подменяются локальными значениями. Уникальный локальный номер задания отличает
новый производственный заказ от повторного нажатия; это не idempotency key СУЗ.
POST подписывается через X-Signature над точными отправляемыми байтами JSON.

Выдача требует ACTIVE, достаточного availableCodes и неизменившегося списка блоков.
ACK проверяется на OMS, UUID блока, количество, отсутствие повторных КИ, GTIN и GS.
Полный блок и все коды фиксируются одной транзакцией. Экспорт JSON возвращает
`block_id`, `order_id`, `gtin`, `codes`; байты строки КМ не преобразуются и не собираются
заново. JSON представляет GS как `\u001d`, при чтении это исходный символ U+001D.

Отчёт наносит только UNIT КМ выбранного владельца/группы со статусом EMITTED.
Проверка выполняется при подготовке и перед подписью. После отправки SUCCESS означает
успех, PARTIALLY — частичный результат, FAILED/REJECTED — отказ. DRAFT, PENDING,
READY_TO_SEND, SENT, CHECK и неизвестные статусы остаются в обработке.
Готовность заказа подтверждается READY, отказ — DECLINED; промежуточные состояния
не трактуются как завершение. Закрытие проверяет фактический CLOSED заказа/буфера.

## True API: ввод, вывод и статусы

| Метод | Назначение |
| --- | --- |
| v3 `POST /cises/info?pg=...` | Статусы и принадлежность КИ |
| v3 `POST /lk/documents/create?pg=...` | MANUAL, тип документа, base64 product_document и отделенная УКЭП подпись |
| v4 `GET /doc/{id}/info?pg=...&body=true&content=true` | Приём, обработка, содержимое и ошибки документа |

Поддержаны JSON `LP_INTRODUCE_GOODS` для производства РФ (OWN_PRODUCTION или
CONTRACT_PRODUCTION) и `LK_RECEIPT` для вывода. Перед отправкой все UNIT КИ должны
принадлежать ИНН выбранного аккаунта и группе; для ввода ожидается APPLIED,
для вывода — INTRODUCED, без дополнительного запрещающего statusEx.
Отправитель и владелец документа сверяются с аккаунтом. Даты вводятся как ГГГГ-ММ-ДД;
будущие даты блокируются. OTHER требует описания причины, первичный документ —
номера и даты при указанном document_type. Остальные групповые поля проверяет True API.

Сохраняются точные байты подписанного JSON. Внешний UUID означает приём;
CHECKED_OK — успех, CHECKED_NOT_OK/PARSE_ERROR — отказ. Остальные статусы остаются
в обработке. В ответе проверяются ID, senderInn, type и productGroup.
Статус документов и последняя проверка КИ отображаются раздельно; код обновляется
по отдельному codes.check без потери полного КМ или локального UUID.

## Журнал и сбои

`prepared → submitting → accepted → processing → succeeded / partial / rejected`.
Операция выдачи может перейти из submitting прямо в succeeded после сохранения блока.
`submitting → unknown` при потере ответа, невалидном ACK, 5xx или аварии процесса.
Подготовка всегда отделена от явной отправки. Изменение намерения в БД обнаруживается
по SHA-256; цели блокируются до выяснения результата. Каждая таблица и связь seller-scoped.

Wire с точными байтами и подписью фиксируется до сетевого вызова. ACK сохраняется
до транзакции результата задания; сбой результата задания не теряет принятый документ.
HTTP API не возвращает wire/подпись. Токены и подписи удаляются из диагностических
ответов; worker пишет только ID задания и класс ошибки. Полные КМ доступны выбранному
локальному аккаунту через экспорт и сохраняются в локальной БД.

Проверки принятых документов начинаются примерно через 30 секунд и продолжаются
при закрытой странице, пока работает приложение. Worker планирует только чтение.
Неизвестные отправки, partial и отклоненные документы автоматически не отправляются.
После подтвержденного HTTP отказа до приёма без внешнего ID возможен явный возврат
в подготовленное состояние; свежие проверки выполняются заново. Ошибка после приёма
или 5xx таким подтверждением не считается.

| Неизвестный результат | Сверка без повторной отправки |
| --- | --- |
| НК feed/sign | Повторное чтение всех карточек и проверка последствий/состава публикации. Для запроса модерации текущих значений недостаточно |
| Заказ/закрытие СУЗ | Ввести ID заказа; поиск квитанции по orderIds, тип/ИНН/OMS/время, точное исходное тело и проверка состояния заказа |
| Отчёт СУЗ | Ввести ID отчёта; поиск по sourceDocIds, тип/ИНН/OMS/время, точное исходное тело и report/info |
| Выдача кодов | Ввести ID нового блока; сверить прежний список, единственный новый блок и количество, получить codes/retry и атомарно сохранить |
| True API | Ввести внешний UUID; сверить отправителя, группу, тип и точное исходное содержимое, затем сохранить внешний статус |

Для квитанции OMS берется из details первого события, а participantInn — из
общих details. docId первого события используется для получения исходного тела.
Время исходного документа должно соответствовать последней попытке отправки
с допуском 5 минут на разницу часов. Проверка текущего состояния НК подтверждает
последствие, но не доказывает, какой клиент его вызвал. Другие клиенты аккаунта
могут работать одновременно; exactly-once между клиентами не обещается.
Если блоков несколько, сверка останавливается. Неизвестные результаты нельзя отменить
как обычный черновик или обойти через generic маршрут операций.

## Границы реализации и приемка

| Сценарий | Локальный предел |
| --- | --- |
| Массовое изменение НК | 1–500 карточек, 1–100 правок атрибутов |
| Подписание НК | 1–10 карточек |
| Заказ СУЗ | 1–10 разных GTIN; до 2 млн КМ при одной позиции, иначе до 150 тыс. на позицию |
| Получение блока / отчёт JSON о нанесении | 1–5000 КМ |
| Проверка КИ / документ оборота / выбор кодов | 1–500 КИ |
| Размер JSON бизнес-документа | 5 МиБ |

Обработчик КИ поддерживает GS1 UNIT `01 + GTIN-14 + 21 + serial`, полный КМ
с GS и кодом проверки. Не заявлены другие структуры кодов, агрегаты/children/uitu,
импортные документы, другие схемы ввода, CSV/XML-документы оборота или печать.
Это границы продукта, а не ограничения всех API ЧЗ. Для товарной группы необходимо
заполнить её обязательные поля и использовать разрешенные шаблоны/производственные условия.

Автотесты проверяют форматы, точные подписи, частичный результат, неподтвержденные ACK,
потерю ответа, явный retry, сверку квитанций/блоков, перезапуск, отдельную фиксацию ACK,
межоперационные блокировки, миграции, FK и изоляцию продавцов. Браузерная приемка
использует тот же worker с изолированным transport/signer, включая всю цепочку операций.
Windows CI отдельно выполняет настоящий DPAPI и проверяет синтаксис PowerShell моста.

Реальная УКЭП/КриптоПро и живой обмен с ЧЗ требуют пользовательского Windows,
действующих сертификата/МЧД, ролей, OMS-параметров и данных товарной группы.
Таких ключей в среде разработки нет; прохождение тестов не является подтверждением
успешных бизнес-транзакций в промышленном ЧЗ.
