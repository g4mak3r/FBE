# Wildberries FBS и передача кодов ЧЗ: этап 4

Flow 0.4.0 добавляет WB в тот же процесс и базу, где работают НК, СУЗ и True API.
Каждый аккаунт, товар, размер, задание, назначение кода и действие относятся к продавцу.
Реальные аккаунты и товарные группы не зашиты в приложение.

## Официальные источники

Проверены доступные официальные спецификации WB 02.10.2026:

- [Авторизация и сведения продавца](https://dev.wildberries.ru/en/docs/openapi/api-information).
- [Товары и склады](https://dev.wildberries.ru/en/openapi/work-with-products).
- [Задания FBS, метаданные и поставки](https://dev.wildberries.ru/en/docs/openapi/orders-fbs?locale=ru).
- [Изменения метаданных за март 2026](https://dev.wildberries.ru/en/news/302).

Прямое чтение сайта из среды разработки возвращало HTTP 498. Использованы
индексированные тексты официальных страниц; это не подтверждает отсутствие последующих
изменений API. Ответы проверяются по форме и идентификаторам. Незнакомые решения WB
не считаются успешной проверкой; живую приемку необходимо провести на аккаунте продавца.

## Подключение и синхронизация

На странице «Wildberries FBS» ввести API-токен категорий «Контент» и «Маркетплейс».
Проверяются срок и категории JWT, затем WB подтверждает `sid`, `tin` и доступ к API.
Декодирование JWT не заменяет внешнюю авторизацию. Токен только на чтение поддержан;
команды недоступны. Тестовый токен не используется для производственного FBS.
Токен защищен тем же Windows DPAPI CurrentUser, что ключи ЧЗ, и не попадает в SQLite,
HTML, журнал или ответы API. Обновление доступа сохраняет идентичность аккаунта и ИНН,
ожидает завершения его операций, удаляет прежний секрет только после успешной замены.

| WB API | Использование |
| --- | --- |
| `GET /api/v1/seller-info` | Проверка аккаунта и ИНН |
| `GET /api/v3/warehouses` | Склады продавца |
| `POST /content/v2/get/cards/list` | Карточки, размеры chrtID, артикулы и штрихкоды |
| `GET /api/v3/supplies` | Все доступные поставки с пагинацией |
| `GET /api/v3/orders` | Задания за фиксированное окно 30 дней |
| `GET /api/v3/orders/new` | Новые задания, включая не попавшие в окно истории |
| `POST /api/v3/orders/status` | Отдельные supplierStatus и wbStatus |
| `POST /api/marketplace/v3/orders/meta` | Метаданные и решения проверки WB |

Последовательность обхода: склады → страницы товаров → страницы поставок → страницы
истории заданий → новые задания. Каждая следующая страница фиксируется в SQLite вместе
с пакетом данных. UUID записей сохраняются при повторном обходе. Ошибка оставляет
успешно загруженные страницы, но не обновляет время последнего полного обхода.
После прерывания чтение перезапускается явно. Кеш не удаляет исторические данные;
отсутствие строки в выдаче не означает удаления или отмены во внешней системе.
Старые задания могут ссылаться на удаленный склад или недоступную поставку: их исходные
внешние IDs сохраняются, отсутствующий FK не подменяется фиктивной записью.

## Товар и код для конкретного задания

1. В «Товары» связать конкретный `nmID + chrtID` с собственной карточкой НК, её GTIN
   и подключенной товарной группой. WB использует производственную среду; ИНН WB и ЧЗ
   должны совпадать. Штрихкоды и артикулы не дают автоматического права объединять товары.
2. В «Задания» выбрать свободные сохраненные полные КМ соответствующих GTIN и группы.
   Один физический КИ резервируется за одним заданием; повторное назначение блокируется,
   включая дублирующие локальные пространства одного аккаунта. Черновик можно отменить.
3. Проверить состав и отдельно отправить. Непосредственно перед передачей True API должен
   подтвердить `INTRODUCED`, владельца, GTIN, группу, упаковку `UNIT` и отсутствие statusEx.
   Проверяется реальное состояние, а не прежняя квитанция о вводе. Печать не является
   условием отправки и не меняет юридический статус кода.
4. WB должен подтвердить `supplierStatus=confirm` и наличие разрешенного поля `sgtin`.
   Другой существующий набор кодов не перезаписывается.
5. `PUT /api/v3/orders/{orderId}/meta/sgtin` передает исходные полные КМ с GS в `sgtins`.
   Полученный HTTP 204 фиксируется как прием запроса. Затем коды повторно считываются
   через метаданные; совпадение набора и `decision=filled` подтверждают завершение.

`metaDetails` имеет приоритет над устаревшим `meta`, удаление которого WB анонсировал
на 30 апреля. `pending` и неподтвержденный результат остаются отдельным состоянием;
причина отказа сохраняется. Принятые действия проверяются worker каждые 30 секунд,
включая закрытый браузер. Передача не создает документ вывода из оборота в ЧЗ.
Разные товарные группы и задания получают независимые действия; нет общего условия
«все коды напечатаны» или «все документы всех групп готовы».

## Поставки

| Команда | Контроль и результат |
| --- | --- |
| Создать | `POST /api/v3/supplies`; имя содержит уникальный суффикс действия для сверки потерянной квитанции |
| Добавить / переместить задания | `PATCH /api/marketplace/v3/supplies/{supplyId}/orders`; проверка склада, cargoType, crossBorderType, B2B/B2C и состояния заданий |
| Прочитать состав | `GET /api/marketplace/v3/supplies/{supplyId}/order-ids`; живые статусы и метаданные, включая IDs вне локальных 30 дней |
| Передать в доставку | `PATCH /api/v3/supplies/{supplyId}/deliver`; непустая активная поставка, задания confirm, подтвержденные метаданные |
| Удалить пустую | `DELETE /api/v3/supplies/{supplyId}`; активная поставка без заданий, отсутствие подтверждается чтением |

Перед передачей в доставку назначенные через Flow коды повторно сверяются с метаданными
WB и True API по группам: последующий вывод кода из оборота блокирует отгрузку.
Для метаданных, добавленных другим клиентом, источником является ответ проверки WB.
Неподтвержденные и неизвестные решения требуют проверки до отправки поставки.

Успех добавления подтверждается чтением состава. Частичный результат сохраняет списки
добавленных и отсутствующих IDs; автоматического повторного добавления нет. Оператор
может подготовить отдельное действие для оставшихся заданий по свежему составу.
`done=true` означает закрытие и ожидание отгрузки; `scanDt` — передачу WB. Flow не
называет эти состояния доставкой покупателю. Состояния исходного ответа доступны отдельно.

## Журнал и восстановление

Migration 005 добавляет связи товаров, резервирование кодов, снимки обхода, действия,
блокировки целей и события. Migrations 001–004 сохранены. Перед обновлением до схемы 5
создается `flow.before-v5.sqlite3`; данные и полные КМ этапов 1–3 сохраняются.

Перед внешней записью сохраняются точное тело, его digest и `submitting`. ACK и итоговая
сверка фиксируются отдельно от коммита worker. Потеря ответа, некорректный JSON, 5xx,
409 и перезапуск во время отправки не вызывают автоматического повтора записи.
При известном отказе до приема можно отменить действие и освободить резерв кода.
Принятые/неизвестные результаты не отменяются как обычный черновик.

«Сверить с WB» читает фактические метаданные, состав или состояние поставки.
Для создания ищется единственное точное имя с суффиксом; несколько совпадений — конфликт.
Если результат передачи кодов неизвестен и WB всё ещё не хранит набор, отдельная кнопка
позволяет явно повторить тот же идемпотентный PUT после свежей проверки. Создание поставки
с неизвестным исходом не повторяется. Во всех случаях запрещена замена чужого набора КМ.

Внешние вызовы имеют таймауты, не следуют редиректам и не используют автоматический retry.
Чтение seller-info кешируется на 60 секунд для каждого защищенного токена.
Интервалы: seller-info — 60 секунд, Content — 650 мс, Marketplace — 500 мс
(учтен лимит базовых токенов 150 запросов/мин);
409 и 429 увеличивают паузу. Контур не обещает exactly-once между разными клиентами WB.

## Приемка и границы

Локально: до 100 кодов/задание, 100 добавляемых заданий/действие, 5000 IDs в читаемом
составе поставки. Товары и локальные коды доступны с пагинацией. FBO/DBS/DBW,
массовое редактирование карточек WB, цены/остатки, пропуска, печать, возвраты и освобождение
ранее успешно переданных кодов для повторной продажи относятся к следующим контурам.

Автотесты и браузерная приемка проверяют цепочку НК/СУЗ/ввода → WB, точные GS,
валидацию, независимые группы, изоляцию, частичный результат, сбои/перезапуск,
защиту от дублей, замену токенов и миграции. Windows CI проверяет настоящий DPAPI;
живой WB, промышленный ЧЗ и УКЭП не представлены тестовыми transport/signer.
Успешные тесты подтверждают реализацию протокола, а не живые бизнес-транзакции.
